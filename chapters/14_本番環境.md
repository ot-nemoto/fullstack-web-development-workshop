# Chapter 14：本番環境への公開

この章では、開発環境と本番環境の違いを理解し、システムを外部に公開するための考え方を学びます。

## 14-1 開発環境と本番環境の違い

### なぜ設定を分けるのか

開発中は「素早く動かすこと」を優先しますが、本番では「安全に・安定して動かすこと」が最優先になります。

| 項目 | 開発環境 | 本番環境 |
|------|----------|----------|
| `DEBUG` | `True`（詳細エラーを表示） | `False`（エラーを隠す） |
| `SECRET_KEY` | コードに直書きでも可 | 環境変数で注入する |
| `ALLOWED_HOSTS` | `['*']`（全ホスト許可） | 公開するドメインのみ |
| データベース | ローカルMySQL | 外部のマネージドDB |
| 静的ファイル | 開発サーバーが配信 | CDNや専用サーバーが配信 |
| HTTPS | 不要 | 必須 |

### DEBUGをFalseにすることの意味

`DEBUG = True` のとき、エラーが発生するとトレースバック（エラーの詳細）がブラウザに表示されます。これは開発中は便利ですが、本番環境では「内部の実装を攻撃者に見せる」ことになり危険です。`DEBUG = False` にすると、エラー時は「500 Internal Server Error」とだけ表示され、詳細は見せません。

## 14-2 環境変数で設定を切り替える

### 環境変数とは

**環境変数**はOSが持つキーと値のペアで、プログラムの外から値を注入できます。コードに秘密情報（パスワード・APIキーなど）を直書きせず、環境変数で渡すことが安全運用の基本です。

```
アプリ起動時
  ↓
OS の環境変数から SECRET_KEY, DATABASE_URL などを読み取る
  ↓
設定ファイルに反映
```

### 🛠️ settings.pyを本番対応に改善する

`backend/config/settings.py` を以下のように変更します。

```python
import os

# SECRET_KEY は環境変数から読む。開発用デフォルト値はローカル専用
SECRET_KEY = os.environ.get('SECRET_KEY', 'django-insecure-local-dev-key-change-this')

# DEBUG は環境変数 DEBUG が 'True' のときだけ True になる
DEBUG = os.environ.get('DEBUG', 'True') == 'True'

# 本番では公開するドメインを指定する。開発中は '*' で全許可
ALLOWED_HOSTS_ENV = os.environ.get('ALLOWED_HOSTS', '*')
ALLOWED_HOSTS = ALLOWED_HOSTS_ENV.split(',')
```

`docker-compose.yml` の `backend` サービスに本番対応の環境変数を追加します（開発環境では `DEBUG=True` のまま）。DB 接続の環境変数は Chapter 13 で追加済みです。

```yaml
services:
  backend:
    environment:
      - SECRET_KEY=django-insecure-local-dev-only
      - DEBUG=True
      - ALLOWED_HOSTS=*
```

本番サーバーでは `DEBUG=False`、`SECRET_KEY` に推測困難な文字列、`ALLOWED_HOSTS` に実際のドメインを設定します。

## 14-3 本番インフラの構成

### PaaSとは

**PaaS（Platform as a Service）** は、サーバーの管理を代わりにやってくれるクラウドサービスです。OS・ミドルウェアの管理をせずに「コードをデプロイするだけ」で公開できます。

代表的なサービスに **Railway** や **Render** があります。Django アプリと Next.js アプリをそれぞれデプロイし、データベースはマネージドサービス（Railway の MySQL など）を使うのが一般的な構成です。

```
[ユーザーのブラウザ]
       ↓ HTTPS
[Vercel / NetlCDの等] ← Next.js フロントエンド
       ↓ HTTPS API リクエスト
[Railway / Render 等] ← Django バックエンド
       ↓
[マネージドMySQL]
```

### デプロイの流れ（概念）

1. **Gitにプッシュ** → PaaS がプッシュを検知
2. **ビルド** → PaaS がコードをビルド（`pip install` / `npm build`）
3. **マイグレーション実行** → `python manage.py migrate`
4. **起動** → アプリサーバーが起動し公開される

CI で「テストが通ったコードのみマージ」→「マージしたら自動デプロイ」という流れを作ると、安全に継続的に本番を更新できます。

## 14-4 セキュリティの基本

### HTTPS

HTTP は通信内容が平文（暗号化なし）で流れます。HTTPS は TLS で暗号化するため、パスワードやトークンを盗聴されません。本番環境では **必ず HTTPS を使います**。PaaS サービスの多くは無料で HTTPS を自動設定してくれます。

### SECRET_KEYの管理

Django の `SECRET_KEY` はセッション・パスワードリセットトークンなどの署名に使います。流出すると攻撃者がこれらのトークンを偽造できるため、**絶対にコードに直書きしてGitで管理しない**ことが鉄則です。

`SECRET_KEY` を新規生成するには Python を使います。

```python
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

生成した文字列を環境変数として本番サーバーに設定します。

### .envファイルの扱い

ローカル開発では `.env` ファイルに秘密情報をまとめて管理することがあります。`.env` ファイルは必ず `.gitignore` に追加し、Git で管理しません。

```
# .gitignore
.env
*.env
```

## まとめ

- 本番環境では `DEBUG=False`・`SECRET_KEY` 環境変数注入・`ALLOWED_HOSTS` 制限が必須
- 環境変数で設定を切り替えることで、コードを変えずに開発・本番を使い分けられる
- PaaS を使うとサーバー管理なしでデプロイできる
- HTTPS・SECRET_KEY 管理・`.env` の `.gitignore` 追加がセキュリティの基本
